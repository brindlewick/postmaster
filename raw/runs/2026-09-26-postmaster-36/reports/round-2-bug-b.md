## 2. Findings

**Finding 1 — P2. An interrupted review round cannot actually be "re-run whole"; retrying after any partial round leaves every scratch reporting SCRATCH BROKEN.**
`skills/postmaster/coachman.md:424-426`:
```
scripts/cut-scratch.sh <repo> <synthesis-wt> "$DEST" "$SNAP" \
  && ( cd "$DEST" && <project build command> >/dev/null 2>&1 ) \
  || echo "SCRATCH BROKEN: $DEST is not cut at $SNAP or does not build; fix before launching $L under $LENS"
```
`scripts/cut-scratch.sh:23`: `git -C "$REPO" worktree add --detach "$DEST" "$SNAP" >/dev/null 2>&1 || { ...; exit 1; }`. The only place a review scratch is removed is at the end of a round that completes normally: `coachman.md:485`, "remove the scratches; `git worktree remove --force` is sanctioned HERE ONLY." `$DEST` (`<repo>/.worktrees/<TICKET>-rev-$LENS-$L`) is not disambiguated by round number, and `coachman.md:438` states "An interrupted round is re-run whole." If the coachman's own process dies mid-round (the same "spent thread" condition Stage D's REMOUNT already exists to handle) after at least one scratch was cut but before the round's cleanup, the resumed leg re-running the round hits `git worktree add`'s "already exists" failure for every such lens/lane, and — because `&&` now gates the build check on that exit code — every one is reported broken, even though the worktree is actually still at the correct commit (no fixes had been applied yet, since fixes only happen after harvest/cleanup). Nothing in the runbook authorizes removing a leftover scratch before this point ("HERE ONLY" restricts the sanctioned force-remove to the post-harvest cleanup), so recovering requires the coachman to deviate from the literal procedure.
Confidence: high. Verified by execution: `scripts/cut-scratch.sh` run twice at the same destination against a disposable one-commit repo — first call exit 0, second call `cut-scratch: git could not create <dest> at <sha>`, exit 1; feeding that exit code through the exact `&&`/`||` line from coachman.md prints "SCRATCH BROKEN... fix before launching" even though the scratch is untouched and correct.
Steps to reproduce: (1) `git init` a throwaway repo, one commit, `SNAP=$(git rev-parse HEAD)`; (2) `scripts/cut-scratch.sh <repo> <repo> <dest> "$SNAP"` — exit 0; (3) run the identical command again (simulating the round being re-run after an interruption, before cleanup ran) — exit 1, "git could not create"; (4) `scripts/cut-scratch.sh ... && (cd <dest> && true) || echo "SCRATCH BROKEN..."` — prints SCRATCH BROKEN.

**Finding 2 — P2. An explicitly-empty per-leg coachman override is silently treated as "no override" instead of being refused.**
`scripts/launch.sh:162`: `spec = (legs.get(leg) if leg else None) or team.get("coachman")`. If `[team.coachman_legs.synthesis]` is present but empty (`{}`), it passes every new check added by this fix — `table()` accepts it (it is a dict), `not_a_lane()` doesn't flag it (`str({}.get("model"))` is `"None"`, not a lane's model) — and then the `or` treats the empty dict as falsy, silently falling through to `team.coachman` with exit 0 and no message. This is exactly the "absence against relative checks" pattern the bug lens is asked to look for: an entry that is present but empty is treated as if it were missing.
Confidence: high on the mechanism; moderate on whether it should be classified as a bug versus intentional behavior (an empty table could be read as "explicitly defer to the default"), but a bare `[team.coachman_legs.synthesis]` section header with nothing under it is an easy, realistic authoring mistake, and 33feb83's extensive new self-test suite for this exact function has no fixture for it.
Verified by execution: a config with `[lanes.one]`, `team.coachman`/`coachman_fallback` set, and `[team.coachman_legs] synthesis = {}` produces `launch.sh form coachman --leg synthesis` → exit 0, using `coach-model` (team.coachman's model), no warning.
Steps to reproduce: write a config with `[team.coachman_legs]` containing `synthesis = {}`, then run `scripts/launch.sh form coachman --leg synthesis` — it succeeds silently on `team.coachman`'s model instead of refusing the empty override.

**Finding 3 — P3. The self-test control for the environment-variable guard doesn't test that guard (test-adequacy gap).**
`scripts/launch.sh:126`: `unset HARNESS MODEL EFFORT ENV_FILE`. `scripts/launch.sh:96`: `refused "a config that does not parse is refused, and the environment's HARNESS and MODEL go unused" dup "cannot read" launch one "$tmp/wt" "$tmp/prompt.txt"`. The `dup` fixture (duplicate TOML key) is caught by the `try/except` around `tomllib.load` (launch.sh:136-139), which calls `die()` and exits before `HARNESS`/`MODEL` are ever consulted — independent of whether the `unset` line runs. On the success path, `eval "$spec"`'s assignments would overwrite any pre-set environment values regardless. So neither the labeled test nor the normal control flow actually depends on the `unset` line; it is currently unexercised by any control.
Confidence: high (execution-verified), moderate on severity — my own analysis suggests the other new fix (the `spec=$(...) && [ -n "$spec" ] || die` wrapper) may already close the original hole independently, making this more a documentation/coverage gap than a live vulnerability today, but it means a future edit could silently drop the `unset` line, or reintroduce a code path where `$spec` is truthy without setting all four variables, with nothing to catch it.
Verified by execution: on a disposable copy of `scripts/launch.sh` with the `unset HARNESS MODEL EFFORT ENV_FILE` line deleted, `--self-test` reports "self-test: all controls behaved," including the control named above.
Steps to reproduce: `sed -i '/^unset HARNESS MODEL EFFORT ENV_FILE$/d' <copy-of-launch.sh>` on a full copy of `scripts/`, then run `<copy>/launch.sh --self-test` — no failures.

**Finding 5 — P3. The resume-prompt file's `k` has no specified or scripted derivation.**
`skills/postmaster/postmaster.md:138-139`: "Write the prompt first to `<dispatch>/leg-<n>-resume-<k>.txt`, `k` counting from 1 for each leg." No script computes `k`, and every resume of a leg (remount, ruling delivery, merge grant/withhold) shares this same sequence per the text itself ("A remount, a ruling and the merge word all reach a leg this way," postmaster.md:151-152). Per the project's own design rule ("Deterministic work goes in scripts/, not in prose... re-derived, and mis-derived, on every run"), a postmaster that miscounts `k` — plausible after being restarted, since "Memory is the disk" and nothing but file-listing would recover the count — could silently overwrite an earlier resume-prompt file. Low operational risk since the actual prompt text is also captured in each leg's own event stream, so this affects only the standalone audit copy.
Confidence: moderate; this is a documentation-completeness observation rather than a demonstrated failure.
Verified by reading.
